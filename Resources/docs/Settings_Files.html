GRIDE Settings Files

What each file holds and where it is; the files themselves hold settings only

GRIDE Help · this page explains toolchain.json entry by entry. The file carries no explanations of its own, so its settings are what one sees on opening it; a tool, an operation and a library keep a one-line description, which the Options pages show.

The file as a whole

EntryWhat it is
the fileThe toolchain GRIDE drives (it was RIDE 5.17's): c90, cpp11 and shalimar compile to assembly for four targets; masm and link (or clang and Microsoft's link.exe for a Debug build) make the Windows program, asm6x and lnk6x the TMS320C6747 program against RTS6x; sim6747 runs it, vm6747 emulates the assembly and debugs; cdb, gdb and lldb debug the host programs; c2s converts between C and Shalimar.

installation - where the toolchain is installed

EntryWhat it is
installationWhere the toolchain is installed. A tool whose lookup says installDir is looked for under <root>\<binDir>; the root is Tools > Options > Projects > 'Installation root or bin' when set, else each defaultRoots entry (environment variables expanded) that holds one of the markers in its binDir, else the folder of GRIDE.exe itself. includeDir and libDir are the installation's header directories the compilers are given (see each tool's installIncludeDirs).

ccs - reading Code Composer Studio projects

EntryWhat it is
ccsReading Code Composer Studio 7.4 / 5.5 projects for the C6747, as White reads them: definitionsDir holds TI's own option definitions (one TSV per compiler major version, keyed by it; CCS stores in .cproject only what differs from the definition's default, so an unstored option's meaning and an enumerated value's spelling come from here); the directory is looked for beside GRIDE.exe, above it, and under the installation. deviceFamily / deviceVariant / siliconVersion say which projects the toolchain builds (others are read, with a note saying why GRIDE would refuse them); compilerDirs name the compiler directory under <CCS root>/tools/compiler per major version; tiRuntime maps TI's library index to the runtime a linker reads.
ccs.tiCompilerTI's C6000 compiler directory (the one with bin\lnk6x), named under Tools > Options > Projects > GRIDE Paths, else the newest one found as CCS's installer leaves them: under each of roots (environment variables expanded), at each of the layouts in under (a trailing * names any folder starting so; an empty entry is the root itself), a folder named as compilerDirs says; bin holds the linker, lib the runtime. A named directory makes a tms6747 build link against TI's runtime instead of RTS6x, as in White.

compilerOptions - the Compiler Options table

EntryWhat it is
compilerOptionsThe Compiler Options (White's options.cpp): the table Tools > Options > Projects > Compiler Options and Project > Properties draw, one entry per option in the order each tab shows them, keyed by id (<tool word>.<option>; general.* serve several compilers). tab, label and hint are the dialog's. control is check (the value is 1 or 0), choice (one of choices; the first is the compiler's own default and is never written) or text (';' between the entries). default is one value, or one per configuration as { Debug, Release }. What an option becomes: flagOn / flagOff for a check (written when the value is 1 / 0), flag for a choice ($(Value) filled in; silent names the choice that writes nothing - the first when absent), flagEach for a text list ($(Item) filled in once per entry, an entry holding a space quoted), environment names a variable the compiler is given instead of a flag (its value 1, or empty). needs says when the option means something: lineTable (the compiler writes a line table for the target), emulated (the emulated target only), notEmulated - with unavailable the sentence said otherwise ($(Arch) filled in); an option that does not apply writes nothing. Each compiler's options field lists the ids it takes, in the order the flags are written; a compiler without one takes its configFlags.

visualStudio - Microsoft's tools and libraries

EntryWhat it is
visualStudioWhere Visual Studio's tools are (cl, ml64, Microsoft's link.exe, clang) and the directories their environment needs, found without cmd.exe: vswhere names the newest installation (any edition, prerelease and Build Tools included), else the defaultRoots are tried; under the installation, msvcTools holds one folder per compiler version with hostBin, lib and include below it - the newest is taken, or the one msvcVersion names ("14.44" takes the newest 14.44.*, Visual Studio 2022's v143; a whole folder name takes that one; empty, or a version not there, the newest) for cl, link.exe, INCLUDE and LIB alike; llvmBin holds clang; the Windows SDK (windowsKits: the registry value, else the roots; the newest version folder) gives the libDirs and includeDirs, $(Version) filled in. environment names the variables set for a tool run: each entry's value is the list of directories joined with ';', followed by the variable's old value.

placeholders - the $(...) words of a command line

EntryWhat it is
placeholdersThe names an argument template may use; GRIDE fills them in when a tool runs. A path placeholder is written without quotes, so a template quotes it where the tool wants quotes.

targets - the platforms built for

EntryWhat it is
targetsThe four targets, keyed by the arch word c90, cpp11 and shalimar take. ideTarget names the IDE's target; host says the programs run on this machine; emulated says the program runs on the emulator or simulator; debugInfo is what a Debug build carries (codeview, dwarf, dwpsn, or empty for none); roles names, per role, the tool id that plays it for this target (nativeAssembler / nativeLinker are the vendor's tools offered when the project's own fail); runtime names the libraries entry linked as the C runtime; run and debug say how a program is started here: program (the program itself), simulator (the simulator's simulate / debug operations), debugger (the debugger's debug operation), none (the target only reaches assembly on this machine).
targets.x86_64-windowsWindows on x86-64: the programs are native and run here; a Debug build carries CodeView through clang and link.exe /DEBUG, a Release build goes through masm and link.
targets.x86_64-linuxLinux on x86-64: the compilers reach assembly here; assembling, linking and running need a Linux machine (as, cc, gdb).
targets.arm64-darwinmacOS on Apple silicon: the compilers reach assembly here; assembling, linking and running need a Mac (as, cc, lldb).
targets.tms6747The TMS320C6747 DSP: the compilers write C6000 assembly, asm6x and lnk6x make the .out against RTS6x, sim6747 runs it, vm6747 runs the assembly straight and is the debugger (through sim6747 --run --debug).

tools - every program GRIDE runs

EntryWhat it is
toolsEvery program, keyed by a stable id the code uses. name is what GRIDE prints; role classifies it (cCompiler, cppCompiler, shalimarCompiler, hostCompiler, hostCxx, assembler, linker, debugAssembler, debugLinker, simulator, emulator, debugger, converter); languages (C, C++, Shalimar) and targets (arch words) say what it serves; exe is the program's file name and aliases the other names tried in order; words are what a project file may call it; lookup says where it is looked for, in order: the environment variable env when set, Tools > Options' tool folder, beside GRIDE.exe, the installation's installDir, then PATH when path is true (vcvars true: Visual Studio's, reached through vcvars64.bat); version is the query that prints its version; outputEncoding is how its output is read (utf-8, or oem for the console's code page); diagnostics names the shape of its error lines (gnu, msvc, shalimar, masm, ti, none); environment lists the variables the tool itself reads; archFlag spells the target ($(Arch) filled in; empty for a tool that builds for the machine it is on); includeFlag / defineFlag are its -I / -D spellings (empty: the tool takes none); installIncludeDirs names the installation directories it is given as includes (include, lib); languageFlags the switch per language; configFlags the flags per configuration, configFlagsByTarget the exceptions per arch - both stand in where the tool lists no options; options names the compilerOptions entries the tool takes, in the order their flags are written (the Compiler Options then make its configuration flags); session, for a tool that debugs, says how it is driven on its standard input: dialect (gdb, lldb, cdb - the shapes its answers are read in), preamble (the commands sent at start), marker and markerCommand (what is asked for after every command, and the text that then ends the answer), commands (the spelling of each thing the IDE asks: break, clearBreakpoints, run, continue, stepOver, stepInto, stepOut, runToLine, args, locals, evaluate, address, type, set, frames, frame, registers, memory, afterMove, where, quit - with $(File), $(Line), $(Expr), $(Name), $(Value), $(N), $(Count), $(Address) filled in); like names a tool whose session this one starts from, its own fields over it; asmSyntaxFlags.codeview is added to a Debug build whose target carries CodeView, asmSyntaxFlags.assemblerNamed when an assembler is named for a host build; operations hold the argument templates, one per thing the tool does, each with the meaning of every argument.

libraries - the runtimes a link takes

EntryWhat it is
librariesThe runtime libraries, as named entries: kind says what each is (runtime, printf, shalimarRuntime, hostCrt); target the arch it belongs to; directory the installation-relative directory holding the files (looked for under the tool folder, beside GRIDE.exe and the installation, in that order; directoryEnv names it outright) and marker the file that proves the directory is the right one; files names the library per configuration (a space-separated list where the link takes several); crt says which host C runtime the entry belongs to (grt, msvc; none: either), so a Windows link takes the hostCrt and the Shalimar runtime of the runtime in force; aliases are the names a project file may use for it, each read as the configuration's file ('*' matches any ending); assemblyDirectories / assemblyDirectoryEnv are where the runtime's assembly is, per configuration, for the emulator; when says when the library is linked: always, shalimar (a Shalimar program), printf (a program calling printf), never.
libraries.rts6xGRIDE's C runtime for the C6747: rts6x.lib built at -O2 for a Release build, rts6xd.lib at -O0 with _DEBUG for a Debug build. A project naming libc.a, rts6740*, rts6747.lib, rts6x.lib or rts6xd.lib gets the configuration's one.
libraries.printf6xRTS6x's printf family in its own library, beside rts6x.lib; linked when a project names it.
libraries.shmrt6xThe Shalimar runtime for the C6747: as a library beside RTS6x (shmrt6x.lib, shmrt6xd.lib for a Debug build) linked before the C runtime it calls into, and as assembly directories the emulator takes (lib\shmrt-tms6747, -debug for Debug).
libraries.shmrtWindowsThe Shalimar runtime for x86_64-windows, which GRIDE's shalimar links itself and GRIDE links with the objects: shmrt-x86_64-windows.lib, and shmrt-x86_64-windows-debug.lib for a Debug build - the runtime with the session in it (SHM_DEBUG=1). Linked first, before the C runtime it calls into. Built by cl over Microsoft's CRT (crt msvc).
libraries.shmrtWindowsGrtThe same Shalimar runtime built by GRIDE's own cpp11, masm and link over GRIDE's runtime (crt grt): shmrt-x86_64-windows-grt.lib, and -grt-debug.lib for a Debug build.
libraries.hostCrtMicrosoft's C runtime (crt msvc), which the Windows link names since the compilers' objects carry no /DEFAULTLIB: the static CRT of the configuration, kernel32 and the legacy stdio definitions. link finds them through LIB (vcvars64.bat). cl's objects do name theirs (/MT, /MTd, /MD ...): a link of cl's objects alone adds none.
libraries.grtGRIDE's own C and C++ runtime for Windows (crt grt): five layered libraries - grtstart.lib (mainCRTStartup), grtcompat.lib (legacy and Microsoft-compatibility names), grtcxx.lib (the Microsoft C++ ABI's support, without exceptions yet), grtc.lib (RTS6x's C library and the Windows stream layer), grtwin.lib (the Windows layer) - and the kernel32.lib GRIDE's link /LIB /DEF writes, all built by GRIDE's own toolchain (toolchain\Windows\RT) and found in lib beside GRIDE ($GRT names the directory outright). A program linked with them needs no Visual Studio and no Windows SDK to build, and kernel32.dll alone to run. Tools > Options > Projects > GRIDE Paths > Windows C runtime decides which runtime a link takes: GRIDE's, Microsoft's, or automatic - Microsoft's only where Visual Studio is found and the build has cl's objects, GRIDE's otherwise (settings.json windowsRuntime: auto, grt, msvc - Black's under environment, Grey's WindowsRuntime, White's windowsRuntime, which White's Tools menu writes; GRIDE_WINDOWS_RUNTIME in the environment at start wins).

3. The .pro project file, key by key

One format for the three outlooks; each writes it the same way, byte for byte, and keeps the keys the other two keep. An object is one key a line; a list of names is one line when it is 90 characters or fewer. // line comments are read, and a save does not keep them.

KeyWhat it is
namethe project's name
toolchainthe compiler word for the whole project - auto (each file's language decides: c90, cpp11, shalimar), or one of them
archthe platform built for - the Target menu's choice: x86_64-windows, x86_64-linux, arm64-darwin, tms6747. A project without one builds for the target chosen in the IDE (Black: any target); none is written until a target other than Windows is chosen
groupsthe files, in named groups: "Sources": ["main.c", "account.c"], or { "files": [...], "toolchain": "c90" } for a group with its own compiler. Paths are relative to the project's folder, with /
includethe header directories the compilers are given (-I)
librarieslibraries the link takes - for a third-party library, its prebuilt binary for this platform
buildwhat the build makes: target is the program (mathx-demo, or mathx-demo.exe on Windows), groups the groups compiled into it, args the program's arguments when it runs. Every Shalimar file has a main(), so for Shalimar the target says which is the program
emulateOnlya TMS320C6747 build that only runs on the emulator (vm6747), not linked for the simulator
optionsthe Compiler Options this project sets, by option id

From Visual Studio to a running program

  1. Open GRIDEd\GRIDE.sln and Build > Build Solution - every project, so the eleven programs land beside GRIDE.exe in x64\<Config>; a build of the GRIDE project alone leaves them out.
  2. Debug > Start Without Debugging: GRIDE starts from x64\<Config>, reads the toolchain.json beside it and %APPDATA%\GRIDE\settings.json.
  3. File > Open: solve3-cpp11.pro - main.cpp comes into the editor with it; Build (F7); Start Without Debugging (Ctrl+F5) runs it.
  4. A C, C++ or Shalimar file open with no project is a program of its own: Build and Start make it in out\<Config>\Win beside the file, and no .pro is written. GRIDE 1.0's Build (Ctrl+B) does the same for its file in front.

Debug without clang. A Debug build needs no clang: c90, cpp11 and shalimar write their source line table and variables as CodeView in the MASM spelling (-g -masm=masm, the compiler's asmSyntaxFlags.ownCodeView - White, which reads no toolchain.json, has the same rule in its code), GRIDE's masm carries it and GRIDE's link, given /DEBUG, writes the PDB that gride-dbg (or cdb) reads - in all three outlooks. Only a compiler without its own CodeView goes through clang (Visual Studio's "C++ Clang tools for Windows" component) and Microsoft's link.exe; without clang such a build is made as Release makes it, and GRIDE says so once.
