GRIDE User Guide

C90 · C++11 · Shalimar — Windows · Linux · macOS · TMS320C6747

1. Getting started

  1. File > New > Project (Ctrl+Shift+N): choose a language, a template, a name, a location and the targets.
  2. GRIDE creates Name\Name.pro with src\, inc\ and lib\ folders, plus a workspace Name.grws.
  3. Choose Config and Target on the toolbar, then press F7 to build.

Before the first build, set the tool paths in Tools > Options > Toolchains. Tools > Toolchain Check shows what is installed.

2. The window

To float a pane, use the button on its title bar or double-click its tab. Close the floating window to dock the pane back. Window > Reset Window Layout restores the default layout.

3. Projects and workspaces

Code Composer Studio projects (7.4 and 5.5) can be opened with File > Open > CCS Project, or added to a workspace. GRIDE reads .project, .cproject and .ccsproject the way RIDE reads them - the device, the compiler version, each configuration's options, defines, include paths, the linker's command file, heap, stack and libraries, excluded files, linked files and folders, a CCS workspace's path variables - and never writes to them. Options CCS left unstored take TI's own defaults from lib\ccs\*.tsv beside the exe. The Output pane (Tools) prints RIDE's Messages lines (what is not supported, where RIDE's own choice stands, what RIDE would refuse and why), and Project > CCS / VS Mapping shows the mapping for the active configuration. Their builds go into the project's .gride\ folder with GRIDE's own tool chain.

Visual Studio solutions and projects (.sln; .vcxproj with its .filters; the classic .vcproj) open through File > Open > Project / Workspace, read only. A solution becomes a workspace with its C++ projects, their dependencies and build order, its solution folders and items; a project becomes a read-only project with the files of its filters, its Debug / Release on x64 (else Win32) as GRIDE's Windows configurations - defines, include directories with the macros resolved, optimisation, libraries - and a note in the Output pane for what is not mapped (property sheets, C++/CLI, MFC, build events). A project that needs Microsoft's headers is built with Microsoft's cl and link.exe when Project > Properties > Compiler names cl: cl then gets the project's own settings too (/W4 /WX /permissive- /EHsc /MT for GRIDE's example, as toolchain.json's projectSettings spells them). The compiler, a folder's compiler and the program's arguments of a read-only project are kept in the workspace's .grws; saving the workspace writes it beside the solution, and the Visual Studio files stay as they were.

4. Building

Each step is a command template with macros such as $(Compiler), $(Source), $(AsmFile), $(ObjFile), $(Objects) and $(Output):

source → compile → .asm → assemble → .obj → link → program (.exe / .out)

  • Errors in MSVC, TI or GNU format appear in the Error List. Double-click one to jump to the line.
  • Build > Batch Build builds several Project · Config · Target combinations in one run.
  • Project > Properties (Alt+F7) edits defines, include dirs, optimisation, libraries and the linker .cmd file for each Config and Target; its Compiler Options tab (also Project > Compiler Options) is RIDE's table per configuration - optimisation, -g, defines and undefines, -nologo, cpp11's --no_compress, shalimar's --debug and --no-search - with the command line each compiler gets shown below.

A build follows RIDE's rules. The Output pane prints $ <folder> (<compiler>) as each part starts, $ linking with ... and [built ...]. A folder may name its own compiler (auto, c90, cpp11, shalimar, cl); a Shalimar program is one compilation of every .shl; a Windows Debug build carries CodeView (clang assembles the GNU spelling, Microsoft's link.exe /DEBUG writes the PDB) and a Release build goes through masm and link; a C6747 build is asm6x and lnk6x against RTS6x (rts6xd.lib / rts6x.lib for every name the project has for the runtime), the Shalimar runtime first for a Shalimar program, the project's .cmd or RIDE's own linker command file; Visual Studio's tools and its INCLUDE / LIB / PATH are found without cmd.exe (the newest compiler version, or the one toolchain.json's msvcVersion pins); a part given to cl is Microsoft's throughout - cl writes the object ([cl] main.cpp -> .gride/obj/Release/main.obj; every progress line names the program that runs and the file it writes), no RIDE header directory stands in front of Visual Studio's, and Microsoft's link.exe links the objects; when the project's own masm / link fail with no fault in the source, GRIDE offers Visual Studio's ml64 and link.exe instead (the native-tools question, Tools > Options > General). Debug > Start Without Debugging (Ctrl+F5) runs the program inside the Output pane with an input line ([program returned N]); on the C6747, sim6747 --run on the .out, Debug > Emulate on VM6747 on the assembly, and Debug > Verify runs both and compares them line for line.

5. The toolchain file and RIDE's settings

GRIDE keeps no tool name, library name or argument convention in its code: toolchain.json beside GRIDE.exe holds them all - every tool (RIDE's c90, cpp11, shalimar, masm, link, asm6x, lnk6x, sim6747, vm6747, c2s, cdb, gdb, lldb, Visual Studio's cl, ml64, link.exe, clang) with its names and aliases, where it is looked for, its argument template per operation, its debugger session; every library (RTS6x, printf6x, the Shalimar runtimes, the host CRT); the Compiler Options rows; the CCS and Visual Studio sections; the C6747 linker command file. Your overrides go in %APPDATA%\GRIDE\toolchain.json (portable: toolchain.user.json beside the exe) and win field by field; edit them under Tools > Options > Toolchains > Definitions (toolchain.json), with Restore shipped defaults per tool and per library, or by hand. A malformed field is reported in the Output pane (Tools) and in Tools > Toolchain Check - the file, the tool, the field - and the shipped value stands. The format is written up field by field in docs\TOOLCHAIN-FORMAT.md.

RIDE's settings.json keys live in gride.settings.json with RIDE's meaning: Tools > Options > Projects > RIDE Paths (the installation's include and lib, the vcvars64.bat whose Visual Studio is used - never run -, TI's C6000 compiler directory and library directory, shared include and library directories, the compiler a new project starts with, the C6747 debugger: auto, sim6747 or vm6747), Tools > Options > Projects > Compiler Options (what a new project starts with), Tools > Options > Projects > Defaults and Locations (RIDE's root, CCS projects on or off, the CCS root), Tools > Options > General (the native-tools question, the indent), Fonts and Colors (the font). A settings file from before the port loads with the new keys at their defaults; nothing was removed.

6. Debugging

F9 toggles a breakpoint (or click the gutter). F5 builds and starts. Then:

  • F10 steps over, F11 steps into, Shift+F11 steps out.
  • Ctrl+F10 runs to the cursor; Shift+F5 stops.
  • Debug > Up the Stack / Down the Stack look at another frame (RIDE's Ctrl+Up / Ctrl+Down); a double-click in the Call Stack does the same, and the top frame is the stop again.

What debugs the build is what RIDE uses, chosen from toolchain.json: a Debug build for the TMS320C6747 runs on sim6747 --run --debug with its .out, or on vm6747 --debug with the assembly; a Windows Debug build runs under cdb on a pseudo-console (Debugging Tools for Windows); a Shalimar Debug build stops itself where no debugger reads it (the program's own session, SHM_DEBUG=1). The Output pane's Debug source says which, and why, in RIDE's words - and when nothing can debug the build (a Release build, a target without a line table), why not; the placeholder then only simulates.

The panes show what RIDE's Debug tab shows. Locals: the stop line on top (stopped at stepped.c:14 in main, with the variables are main's, at ... when a frame above is looked at), the variables as Name | Value | Type | Address, a value changed since the last stop in red, the engine's reason in brackets when there are none (a Shalimar program says where it is, not what is in it), the keys line along the bottom; the line above it sets a variable (name = value, Enter; Enter on a row fills it in). Watch: the expressions read again at every stop and frame change, a refused one in grey, add a watch... last - the line under the list adds one, Enter on a watch brings it there to be changed, an empty answer takes it away. Call Stack: the frame looked at in bold. Registers and Memory read the engine (the C6000's registers under the emulator and simulator; cdb's r and db). The program's own output comes through the Debug source as it prints.

7. C ↔ Shalimar conversion

Use Tools > Convert (Ctrl+Alt+S for C → Shalimar, Ctrl+Alt+H for Shalimar → C). The converter is toolchain.json's c2s (--to-shalimar / --to-c), found beside GRIDE.exe or as its lookup says; Tools > Options > Converters can name another program or command template instead. GRIDE can add the result to the project and open it.

10.3 Debug and Release: optimization

Build ▸ Configuration ▸ Debug / Release (Ctrl-D in the console editor) chooses how everything is compiled. The status bar shows which.

CompilerDebugRelease
c90, cpp11-g -D_DEBUG=1-O2 -DNDEBUG=1
host c++ group-g -D_DEBUG=1-O2 -DNDEBUG=1
cl group/Od /Zi/O2
shalimar--debug(no -O)
  • Debug is -O0 - no optimisation - and carries debug information.
  • Release optimises: cpp11 -O2 runs its optimizer (register allocation, copy propagation, loop alignment, inlining); for tms6747 it also schedules the C6000's instructions to their delay slots. -O1 and -O2 are the same passes today.
  • The choice belongs to the machine, not the project: it is kept in ~/.ride/state.json, and a "config" key in a .pro is ignored - a project that travels does not put everyone who opens it into Release.
  • On the command line: cpp11 -O2 prog.cpp -o prog (or -O1, or -O0, the default); c90 -O2 the same.

In GRIDE: the Config box on the toolbar chooses Debug or Release, and the status bar shows it. The choice is kept in the workspace (.grws), not on the machine. The flags are RIDE's, from the Compiler Options table: Project > Compiler Options for one project, Tools > Options > Projects > Compiler Options for new projects (section 4). cl takes the cl group's flags from toolchain.json; a Visual Studio project compiled by cl also gives it the project's own settings (/W4 /WX /permissive- /EHsc with /MT for Release and /MTd /RTC1 for Debug in GRIDE's example, section 3).

10.6 The project file (.pro)

One JSON object; // comments are allowed.

{
  "name": "demo",
  "toolchain": "auto",           // auto | c90 | cpp11 | shalimar | c++ | cl
  "arch": "x86_64-windows",      // the target: one of the four
  "include": ["third_party/x/include"],      // extra header directories
  "libraries": ["third_party/x/libs/x.lib"], // extra objects and libraries
  "groups": {
    "Sources": ["main.c", "greet.c"],
    "Headers": ["greet.h"]
  },
  "build": { "target": "demo", "groups": ["Sources"] }
}
  • groups name the files shown in the left pane; a group may set its own "toolchain" (e.g. "c++" for the host's compiler).
  • build names the program the build makes (target - demo, or demo.exe on Windows) and which groups go into it.
  • Shalimar: every file has a main(); target names the file whose main() is the program, and a call to a function another project file defines is found there.
  • No build: nothing is built, and Ctrl-B still compiles the open file.

In GRIDE: GRIDE's .pro is GRIDE's own JSON format, not RIDE's. It holds the language, the targets, folders and files (paths relative to the .pro), the configurations, the compiler per folder, the program's arguments and RIDE's Compiler Options (README, section 3). RIDE's group "toolchain" is GRIDE's compiler per folder, under Project > Properties. A CCS or Visual Studio project has no .pro and its own files are never written: its compiler, compiler per folder and program arguments are kept in the workspace's .grws instead (GRIDE's example says "toolchain": "cl" there).

10.7 A third-party library: include path and binaries

A library usually arrives as a header directory and prebuilt binaries. The project file carries the whole provision:

  • "include" - its header directories; every compile gets each as -I.
  • "libraries" - its binary files (.a / .o on macOS and Linux, .lib / .obj on Windows); each is handed to the link. Name each file.

Both lists are relative to the project, and Project ▸ Include Paths… / Libraries… edit them. Option ▸ Shared Include Paths… / Shared Libraries… hold the same two lists for every project, in settings.json.

thirdparty-mathx is the worked template: third_party/mathx/include, a libmathx.a built by clang for macOS and a mathx.lib built by Visual Studio for Windows. Open mathx-macos.pro on a Mac and mathx-windows.pro on Windows - they differ only in "arch" and the one library. A library made by another compiler links when its interface is C (extern "C"); one that passes std::string or std::vector across its interface does not, since RIDE's C++ library is its own.

In GRIDE: a project's include directories and libraries are set per configuration and target under Project > Properties. The shared ones every project gets are under Tools > Options > Projects > RIDE Paths. The rule about interfaces holds unchanged: GRIDE builds with RIDE's compilers and RIDE's C++ library.

10.8 Windows: the assembler and clang

Inside RIDE, settings.json names masm as the x86_64-windows assembler, so RIDE builds need nothing from Microsoft to assemble. On the command line, cpp11 writes the GNU spelling by default, which clang assembles - the only spelling that lets a program of several C++ files share inline functions (COMDAT). cpp11 finds clang in any Visual Studio 2022 edition that has the C++ Clang tools component (Visual Studio Installer ▸ Individual components), in a standalone LLVM, or on PATH; with none, it assembles with masm instead and says so - enough for a one-file program.

To use masm yourself, ask for its spelling:

cpp11 -S -masm=masm hello.cpp -o hello.asm
masm -t x64 hello.asm -o hello.obj          (or masm /c /nologo /Fo hello.obj hello.asm)

A .s from plain cpp11 -S is clang's spelling and masm will not read it.

The link: link and lnk6x are RIDE's own. When one of them itself fails a build - not for the program's own link error, such as a missing main - RIDE asks whether to use Visual Studio's link.exe (or TI's lnk6x) for that build - found through vswhere or the directory Option ▸ Linker for tms6747… names; "askNative": false in settings.json never asks.

Real C674x silicon (.out / .hex): bin\ti\ti-build.cmd <program> builds a linked .out and Intel .hex with a Texas Instruments Code Generation Tools install already on the machine (none of TI's tools ship with RIDE); see bin\ti\TI-BUILD.txt.

In GRIDE: the same choices are made in toolchain.json. A Windows Release build assembles with masm and links with RIDE's link. A Windows Debug build writes the GNU spelling, which clang assembles, and Microsoft's link.exe /DEBUG writes the PDB. If clang or link.exe is missing, the build goes on with masm / link and says so. Files compiled by cl are Microsoft's objects, and Microsoft's link.exe links them in both configurations. Visual Studio's tools are found without cmd.exe. The native-tools question is RIDE's askNative, under Tools > Options > General (section 4). TI's C6000 compiler directory goes under Tools > Options > Projects > RIDE Paths.

10.10 Removing RIDE

  • Windows: Settings ▸ Apps ▸ RIDE ▸ Uninstall.
  • macOS: sudo rm -rf /Applications/RIDE.app /usr/local/ride, the links in /usr/local/bin (ride c90 cpp11 shalimar c2s vm6747 asm6x masm lnk6x), and sudo pkgutil --forget com.ghulamrs.ride.
  • Linux: /opt/ride/uninstall.sh (or <prefix>/uninstall.sh).

Documents/RIDE is yours and is never removed.

In GRIDE: GRIDE has its own installer and its own entry under Settings > Apps; removing one of RIDE and GRIDE leaves the other installed.
