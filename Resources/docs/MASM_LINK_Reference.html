MASM / LINK

GRIDE's own Windows assembler and linker, and the debug information they carry

A Windows build goes source → compile (-masm=masm) → .asm → masm → .obj → link (+ the CRT) → .exe. masm reads Microsoft's MASM syntax and writes the COFF object ml64 would; link takes link.exe's command line and writes the PE32+ image. Both are built with GRIDE, beside GRIDE.exe.

masm and CodeView

A native Windows debugger (cdb, WinDbg, Visual Studio) finds its way through a program by CodeView: the line tables and procedure records an object carries in .debug$S, which a linker's /DEBUG gathers into a .pdb. masm writes them, as ml64 /Zi and cl lay them out:

Asked byWhat the object gets
/Zi or /Zd (ml64's spelling), -ga line record for each line of the .asm that makes code - the debugger steps through the assembly itself, as with ml64 /Zi
a .FILE and .LINE in the source (no option needed)line records for the source lines those directives name - the C, C++ or Shalimar a compiler made the assembly from - and none for the .asm's own lines

Either way the object's .debug$S holds S_OBJNAME and S_COMPILE3, and for each PROC an S_GPROC32 (S_LPROC32 for a private one) with its size and where its prologue ends, an S_FRAMEPROC made from its unwind directives (.ALLOCSTACK, .PUSHREG, .SETFRAME), and S_END; a line table per PROC (and per run of code outside every PROC); the file table and the string table. A PROC in a COMDAT section has its records in a .debug$S of its own, associative to that section, so the linker keeps them with the copy it keeps. Without /Zi and without .FILE, an object has no .debug$S, as before.

The source-line directives

ml64 has no words for "this instruction came from line 12 of main.c"; these two are masm's own. A compiler writes them under -g with -masm=masm.

DirectiveMeaning
.FILE n, "path"source file n (1 to 65535) is path. Write the path absolute - a debugger matches a breakpoint's file by it; a relative one is taken from the directory masm runs in. A MASM string: backslashes as they are, a quote doubled. Naming the same number again with the same path is allowed, with another path an error.
.LINE line [, n]the instructions that follow come from line (1 to 16777215) of file n. Without n: the file of the .LINE before it in the PROC, else file 1. File n must have been named by a .FILE above.
  • A .LINE holds until the next one or the ENDP of its PROC. The first instruction after it starts the line's record; a .LINE no instruction follows records nothing, and a second .LINE naming the line already in force starts a second record of that line at the next instruction - how a compiler marks where a one-line function's body starts, after its prologue, so a debugger stops there with the parameters stored.
  • A file with any .LINE is described by its .LINEs alone. Code they do not cover - a PROC without one - gets no line, though /Zi was given.
  • The language recorded (S_COMPILE3, which decides how a debugger evaluates an expression) is taken from file 1's extension: C++ for .cpp, .cxx, .cc, C for .c and every other source; MASM for a file with no .FILE.
  • The directives are not ml64's: assembly carrying them is for masm. Without -g the compilers write none, and their output stays what ml64 assembles.

A compiler's own CodeView

The line tables are masm's; what a debugger shows of variables - parameters, locals and blocks (S_REGREL32, S_BLOCK32), statics and globals (S_LDATA32, S_GDATA32), and their types - only the compiler knows. Under -g -masm=masm, c90 and shalimar write those records themselves, as data in two segments masm carries into the object as they are:

In the sourceIn the object
.debug$S SEGMENT ... .debug$S ENDSthe .debug$S section (discardable): the compiler's symbol records, then masm's line tables, file table and string table after them. With a .debug$S of the source's, masm writes no procedure records of its own.
.debug$T SEGMENT ... .debug$T ENDSthe .debug$T section: the types, numbered from 0x1000
DD SECTIONREL labelthe label's offset in its section (ml64's operator)
DW SECTION labelthe number of the label's section - masm's own operator: with SECTIONREL it is how CodeView names an address

The two segments are 4-aligned, so ALIGN 4 pads a record; a label difference (DW end - start) gives a record its length.

EXTRN ExitProcess:PROC
    .FILE 1, "D:\work\twice.c"
.CODE
twice PROC
    .LINE 3
    mov eax, ecx
    .LINE 4
    add eax, eax
    .LINE 5
    ret
twice ENDP
END

link and /DEBUG

/DEBUG writes a program database beside the image - prog.pdb for prog.exe, or the file /PDB:file names - and gives the image a CODEVIEW debug-directory entry (an RSDS record) naming the .pdb by its full path, with the GUID and age they share. A debugger opens the .pdb whose GUID and age match; the GUID is a hash of the image, so the same link makes the same pair. As with link.exe, /DEBUG implies /OPT:NOREF and /OPT:NOICF, and /DEBUG:NONE turns it off. Without /DEBUG the image is what it was before.

In the .pdbMade of
a module per object and archive memberits .debug$S, relocated: the symbols (procedures, blocks, frames, data), the line tables and the file table - each .debug$S that goes with a COMDAT the link dropped is dropped with it
the globalsS_PROCREF per procedure, and the file-scope data and UDTs
the publicsS_PUB32 per external the image holds, and their address map
DBIthe section contributions, the section map, each module's source files, and the image's section headers
/namesthe source file names the line tables point at
TPI, IPIevery object's .debug$T merged - types into TPI, ids (LF_FUNC_ID and the rest) into IPI - each record once, every index in the records and the symbols rewritten to the merged numbering, with the hash streams a debugger finds a type by name through (how a pointer's forward-declared struct is resolved). An object whose types are in a type server (LF_TYPESERVER2, as much of the C runtime's) or a precompiled header keeps its symbols with no types.

The layout is the MSF one LLVM documents and lld-link writes; it reads back through dbghelp (cdb, WinDbg), DIA (Visual Studio) and llvm-pdbutil. So a Debug build needs neither clang nor Microsoft's link.exe: c90 -g -masm=masm (or shalimar -g -masm=masm), masm, and link /DEBUG make a program a debugger stops in at file.c:line, steps line by line, shows the parameters, locals and globals of with their types, and walks the stack of, the C runtime's frames included.

link /LIB: libraries

link /LIB is the librarian, as link.exe /LIB is lib.exe. What it writes is the archive link.exe and lib.exe read: both linker members (the second sorted, for a binary search), the longnames member when a name passes fifteen characters, the members on even offsets, every header dated -1 so the same inputs make the same file. @file on either command line reads its words from the file, which is how a library of a few hundred objects is named under Windows' 32,767 characters.

CommandWhat it does
link /LIB /OUT:x.lib a.obj b.obj ...an archive of the objects, indexing every external each defines (a weak external is not indexed); a name two members define is said, unless both define it in a COMDAT - an inline function each translation unit emits
link /LIB /DEF:x.def [/NAME:dll] /OUT:x.liban import library for the DLL the .def's LIBRARY names: its import descriptor, the null descriptor and null thunk, and one short import member per export (DATA ones without the jump thunk, PRIVATE ones left out) - the SDK's import libraries' layout, so link builds the import table from it as from theirs
link /LIB /LIST x.libeach member, and the externals it defines

GRIDE's runtime for Windows is made this way: five layered libraries - grtstart.lib, grtcompat.lib, grtcxx.lib, grtc.lib, grtwin.lib - from the objects c90, cpp11 and masm make of it, and kernel32.lib from toolchain\Windows\RT\kernel32.def - no SDK library is read. A program linked with them needs no Visual Studio and no Windows SDK, and imports KERNEL32.dll alone (docs\Runtime_Design.md).
