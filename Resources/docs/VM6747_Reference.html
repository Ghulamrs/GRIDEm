VM6747 / SIM6747

The two ways GRIDE runs a TMS320C6747 program

A TMS320C6747 build goes source → compile → .s → asm6x → .obj → lnk6x (+ RTS6x) → .out. GRIDE can run the program at two points of that chain:

vm6747 - the emulatorsim6747 - the simulator
Runsthe assembly the compilers write (.s, or a .vm folder of them) - nothing is assembled or linkedthe linked program (.out) that asm6x and lnk6x make against RTS6x - the build's final output
In GRIDEEmulate on vm6747 - the Debug menu in Black and Grey, the Build menu in White; also Run for a Black or Grey project marked Emulate only (Project > Properties), which stops at the assemblyRun on the TMS6747 target: Ctrl+F5 in Black, F5 (build and run) or Ctrl+F5 in Grey, F5 in White
Command linevm6747 "<prog>.s" [Shalimar runtime dir] [arguments]sim6747 --run -c "<prog>.out" (takes no command line for the program)
Debugging (F5 in Black, F8 in Grey and White)vm6747 --debug "<prog>.s" - when there is no .out of this build with a line tablesim6747 --run --debug "<prog>.out" - when the .out is this build's and carries a line table (-g)
Found through%VM6747%, then beside GRIDE.exe, then PATH%SIM6747%, then beside GRIDE.exe, then PATH
  • Verify (the Debug menu in Black and Grey, the Build menu in White) runs the program both ways and compares the output line for line ([verify] the two agree, line for line): the assembly on vm6747 against the linked .out on sim6747.
  • Black and Grey can fix the debugger in use under Tools > Options, on the RIDE Paths page (auto, sim6747, vm6747); in every outlook GRIDE_DEBUG_SIM6747=1 or GRIDE_DEBUG_VM6747=1 in the environment at start wins.
  • A Shalimar Debug program under sim6747 stops itself (SHM_DEBUG=1): its own session, which stops by statement (GRIDE's Help).
  • For Black and Grey, both tools, their arguments and their debugger sessions are entries in toolchain.json (vm6747: emulate, launch, debug; sim6747: simulate, debug, session).
